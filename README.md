# 🌸 指尖花开 · Gesture Bloom

用摄像头识别手部 21 个关键点，**握拳花朵闭合为花苞，张开五指粒子向外绽放**，手掌移动时花朵跟随。

Three.js GPU 粒子 · MediaPipe Hands · 原生 JS/HTML/CSS · 无构建步骤。

---

## 快速开始

**方式一：双击启动（推荐）**

在资源管理器里双击项目根目录的 **`启动.cmd`**，会自动启动服务器并打开浏览器。

**方式二：命令行**

```bash
node server.js          # 默认 http://localhost:5173
node server.js 8080     # 指定端口
```

打开浏览器访问 **http://localhost:5173**，点击「开启摄像头，开始体验」，允许摄像头权限。

**方式三：部署到 GitHub Pages（HTTPS，任何人在线可用）**

见 [PUBLISH.md](PUBLISH.md)。双击 `发布.cmd` 即可，脚本内置了网络重试。

> ⚠️ **必须通过 HTTP 服务访问，不能直接双击 `index.html`。**
> 浏览器的 `getUserMedia` 只在**安全上下文**（`https://` 或 `http://localhost`）下可用。
> 用 `file://` 打开会被浏览器直接拦截，页面上会给出对应提示。

没有摄像头、或不想授权？点「跳过摄像头，使用自动演示 →」，会播放一段模拟的握拳→张开循环。

> 💡 `启动.cmd` 会自动查找 Node.js（PATH → 常见安装目录 → 便携版）。
> 如果系统里完全没有 Node，它会自动改用 PowerShell 内置服务器 `_serve.ps1`，功能完全一样。

### 依赖说明

| 依赖 | 来源 | 大小 |
|---|---|---|
| Three.js r160.1 | **本地 `./vendor/three/`** | 1.3 MB |
| MediaPipe Hands | **本地 `./vendor/mediapipe/`** | 18 MB |

两者都已本地化，**首次启动无需等待下载**，也能离线运行。
`js/config.js` 里保留了 CDN 作为回退源，本地文件缺失时会自动改用 unpkg / jsdelivr。

> ⚠️ **为什么一定要本地化 MediaPipe？**
> 它需要下载约 18MB（其中 6MB 的 WASM 单文件在慢网络下实测可卡 **40 秒以上**，
> 日志停在 `still waiting on run dependencies: wasm-instantiate`）。
> 走 CDN 时用户点了「开启摄像头」后会长时间毫无反应，体验很差。

> 📌 **不要把 MediaPipe 的 `hand_landmark_full.tflite` 换成别的来源。**
> 正确文件是 **5,478,688 字节**。曾用某个来源拿到 4,926,547 字节的版本——
> 它的头部魔数同样是 `TFL3`，看起来完全正常，但内容被截断，
> MediaPipe 会报 `No subgraph in the model` 然后 WASM abort。
> 若怀疑文件损坏，用下面命令核对大小：
> ```bash
> node -e "const f='vendor/mediapipe/hand_landmark_full.tflite';console.log(require('fs').statSync(f).size)"
> ```

## 操作方式

### 主控：张开度

| 手势 | 效果 |
|---|---|
| ✊ 握拳 | tension → 0，粒子聚合收拢成花苞 |
| 🖐 张开五指 | tension → 1，花瓣**螺旋绽放** + 抽出花瓣流光 + 冲击波光环 |
| ✋ 移动手掌 | 花朵跟随手掌平移，并带轻微拖尾 |

### 进阶动作

| 动作 | 效果 | 怎么用 |
|---|---|---|
| ☝️ **单指抽出花瓣** | 花瓣被吸向指尖并跟随移动 | 只伸出**食指**，其余手指握起；指尖往哪移，花瓣就被拉向哪 |
| 🔄 **手指旋转 → 花朵旋转** | 整朵花跟着手掌转动 | 手腕左右**转动**（像拧钥匙），花朵同步旋转；花苞状态转动更醒目（×1.35） |
| 🤏 **捏合缩放** | 花朵整体放大 / 缩小 | 拇指与食指**捏合**变小，**张开**变大 |
| 👋 **挥手吹散** | 花瓣被一阵风吹开，然后自己飘回来 | 手掌**快速水平挥动** |
| 🖐 **五指全开脉冲** | 绽放瞬间来一次强化脉冲 + 光环 | 从握拳**猛地张开**五指 |

### 键盘

| 键 | 作用 |
|---|---|
| `1` ~ `6` | 直接切换到对应形态 |
| `Tab` / `←` `→` | 循环切换形态（`Shift+Tab` 反向） |
| `空格` | 切换自动演示 |
| `C` / `H` | 显示/隐藏摄像头画面 / 手部关键点 |
| `R` | 重置视角与旋转 |

右上角按钮与左侧形态面板提供同样的开关。

> 💡 **单指追踪与「张开五指」不冲突**：只有**食指单独伸出**（其余四指都握起）时才激活指尖牵引；
> 五指全开走的是正常的绽放逻辑。

## 模型加载（这是部署后最容易踩的坑）

手部识别模型约 **16 MB**，是整个项目里最脆弱的一环。记录一下实测数据和最终方案。

### 实测到的三个问题

| 问题 | 实测数据 |
|---|---|
| GitHub Pages **不压缩** `.wasm` / `.data` / `.tflite` | `Content-Encoding: 无`，6 MB 的 WASM 原样传输 |
| `Cache-Control` **只有 10 分钟** | `max-age=600`，过期后 16 MB 要重下一遍 |
| 并行请求**互相抢带宽** | 7 个文件同时下时，一个 276 KB 的文件用了 **86.6 秒**（≈3 KB/s）；单文件顺序下能到 38 KB/s |

后果：国内从 GitHub Pages 加载要 **7 分钟以上**，
而原来的代码 **90 秒就超时放弃** —— 所以永远进不去，
界面上还只有一个"已等待 N 秒"的死画面。

### 现在的方案

1. **页面一打开就在后台预加载**，不等用户点「开启摄像头」。
   用户看说明的那几秒就是在下载。
2. **串行下载**，避免前面测到的抢带宽问题。
3. **实时进度条**（`3.2 MB / 16.0 MB`），不是转圈。
4. **Service Worker 缓存**（`sw.js`）——把资源存进 Cache Storage，
   不受 GitHub 那 10 分钟的限制，**第二次打开是零网络流量的**。
5. 超时从 90 秒放宽到 300 秒。

### 怎么验证的

判据不能用「耗时变短」——在 localhost 上一切都在 100ms 内，
按耗时判断会把"真的下载"误判成"命中缓存"
（实测在**全新**缓存上也报过 6/7 命中）。

所以 `_test/sw-cache-check.mjs` 用 **Service Worker 主动上报的命中事件**作为直接证据：

```
第 1 次访问  servedFromCache=0   cachedInStorage=7   ← 真的下载了，并全部写入缓存
第 2 次访问  servedFromCache=7   cachedInStorage=7   ← 全部由 SW 直接给，网络零流量
```

并按字节数逐个核对缓存内容（WASM 6,026,259 / 模型 5,478,688）。

### 还能更快吗

能，但没有做（会牺牲准确性或增加复杂度）：

- **换 lite 模型**：`hand_landmark_lite.tflite` 只有 2.07 MB（full 是 5.48 MB），
  省 3.4 MB。但手势阈值是按 full 模型调出来的，换了要重新标定。
- **自己 gzip**：实测 17.38 MB → 10.81 MB（省 38%，WASM 单文件省 70%）。
  需要额外存 `.gz` 并让 Service Worker 用 `DecompressionStream` 透明解压。
- **换国内可访问的托管**：GitHub Pages 走 Fastly，国内被限速。
  这是根本瓶颈，代码层面无法绕过。

> 💡 如果加载特别慢，可以先用「跳过摄像头，使用自动演示」看粒子效果，
> 模型在后台继续下载，好了再点「开启摄像头」。

## 形态变换

同一批 18000 个粒子可以在 **6 种形态**之间平滑变换，
在 GPU 上完成，切换时不需要重建几何体。

| 形态 | 说明 |
|---|---|
| 🌸 **花朵** | 默认形态，随手势绽放/合拢 |
| 🦋 **蝴蝶** | 双翼展开，会持续扇动 |
| 🌌 **星系** | 四条对数螺线旋臂，较差自转 |
| 💗 **心形** | 心形参数方程轮廓，带心跳 |
| 🔥 **凤凰** | 双翼羽枝展开 + 下垂尾羽 |
| 🐋 **鲸鱼** | 侧视剪影 + 摆动的尾鳍 |

### 实现方式

每个粒子多带一组 `aPosMorph` 属性存放目标形态位置，顶点着色器做三级混合：

```glsl
vec3 flowerPos = mix(aPosBud, position, localSpread);   // ① 花苞 ↔ 绽放
vec3 pos = mix(flowerPos, aPosMorph + arc, uMorph);     // ② 花朵 ↔ 目标形态
```

其中 `arc` 是变形中途的弧线扰动——`uMorph` 在 0.5 附近时位移最大，
粒子像被抛出去一样划过一段弧线，比直线插值生动得多。

切换形态时只写入 `aPosMorph`，真正的过渡由 `uMorph` 缓动完成（约 2 秒）。

### 踩过的坑（这部分花的时间最多）

**1. 片段着色器的 uniform 必须在两个着色器里都声明。**
我在片元里用了 `uMorph` 却只在顶点声明，结果
`Fragment shader is not compiled: 'uMorph' : undeclared identifier`——
整个花朵退化成无法辨识的模糊光云。
危险的是「覆盖率/亮度」这类统计量看起来仍然"正常"，很容易误判。
现在 `morph-check` 会**最先**检查着色器编译错误。

**2. 各形态必须统一居中与缩放，而且要按「最大半径」而不是「包围盒」。**
各生成器的自然尺寸差异极大（实测凤凰 X 范围 `-4.36~1.46`、蝴蝶 Y 范围 `-1.47~2.95`），
不处理就会「一个又偏又大、一个又小又挤」。

更要紧的是归一化方式：最早我用**包围盒跨度的一半**做归一化，
但包围盒只保证轴向不超出，**对角方向的点可以到 1.41 倍**。
蝴蝶/星系/心形都是近似圆形的平面图形，正是这种情况——
实测屏幕垂直占比达到 **110~122%**，直接溢出视口，
用户看到的就是「形状显示不出来，只剩一圈弧线」。

改成按**最大半径**（到中心的最远距离）归一化后，所有形态最外点都落在同一球面上，
必定完整入镜。`morph-check` 里现在有断言把「不溢出 + 高度 > 20%」固化下来。

居中则用**包围盒中心**而不是质心——质心会被粒子密集处拉偏，
凤凰按质心居中后包围盒仍然偏左。

**3. 花朵专属的变形必须按 `uMorph` 淡出。**
「花瓣涡旋」旋转的是 `pos.xz`，而形态数据是立在 `XY` 平面的平面图形。
不淡出的话平面图形会被"拧"出平面，变成一条斜向的糊状带（心形完全不可辨）。
同样需要淡出的还有：呼吸缩放、指尖牵引、整体自转、相机俯角。

**4. 平面形态不能绕 Y 轴自转，而且必须把角度转回 0。**
花朵态持续绕 Y 自转，形态态若只是"停止累加"，角度会冻结在切换那一刻的值
（实测心形被冻在 90° 附近）。必须主动平滑归零（走最短路径）。

**5. 星系盘要建在 XY 平面。**
按常规做法建在 XZ 平面的话，倾角归零后会变成 edge-on 的一条细线，
完全看不出旋臂（实测只剩一条水平亮线）。

**6. 形态要把粒子铺在轮廓上，而不是填满内部。**
均匀填充会让中心密度极高，加法混合下直接烧成白斑，形状反而看不出来。
各形态现在都用 `pow(rand, 1.35~2.6)` 让粒子偏向轮廓/表面。

> ⚠️ 凤凰形态是六个里最"勉强"的一个：它结构最复杂（羽枝 + 身体 + 尾羽），
> 在 18000 粒子的预算下细节会被平均掉。
> 如果觉得不够像，可以在 `js/shapes.js` 的 `makePhoenix` 里
> 把 `featherIdx` 的羽枝数量从 6 提到 8~10，或减少尾羽、把粒子集中给翅膀。

## 特效系统

所有特效都在 GPU 上完成（`js/effects.js` + `js/shaders.js`），不增加 CPU 负担。
各层粒子数：主体 12000 · 花瓣流光 2200 · 逸散花粉 1300 · 冲击波光环 700。

### 1. 花瓣散开 / 合拢

由 tension → spread 驱动，顶点着色器在「花苞位置」与「绽放位置」之间插值：

```glsl
vec3 pos = mix(aPosBud, position, localSpread);
```

### 2. 螺旋绽放（依次打开，而非同时）

花瓣不是一起张开，而是**按角度顺序依次打开**，视觉上是旋转着绽开：

```glsl
float petalPhase = fract(aPetal / 6.2831853);
float delay = petalPhase * 0.42 + aLayer * 0.18;   // 外圈先开、内圈后开
float s = clamp((uSpread - delay * 0.6) / (1.0 - delay * 0.6), 0.0, 1.0);
float localSpread = s * s * (3.0 - 2.0 * s);
```

### 3. 花瓣涡旋 + 整体自转

每片花瓣一边打开一边绕中轴扭转；整朵花还有一层由**手指旋转**驱动的刚性自转（`uSpin`）：

```glsl
// 花瓣自身涡旋
float petalTwist = localSpread * 0.35 * (1.0 - petalPhase * 0.5);
// 手指旋转带来的整体自转（可连续转多圈）
pos.xz = mat2(cos(uSpin), -sin(uSpin), sin(uSpin), cos(uSpin)) * pos.xz;
```

`uSpin` 用的是**累积角**：手掌转多少，花朵就转多少，转好几圈也不会跳变
（`GestureTracker` 里处理了 ±π 跳变）。

### 4. 单指牵引花瓣

食指单独伸出时，指尖附近的花瓣被高斯衰减的力场拉向指尖：

```glsl
vec2 toFinger = uFinger * 2.3 - pos.xy;
float influence = exp(-dot(toFinger, toFinger) * 0.42);   // 影响半径 ~1.8 单位
float pullStrength = uFingerActive * (0.62 - localSpread * 0.30);
pos.xy += toFinger * influence * pullStrength;
```

花苞时牵引更强（像用手指把花瓣一点点抽出来），张开后减弱。
同一套逻辑也作用在「花瓣流光」层上，流光会汇聚到指尖。

### 5. 抽花瓣（花瓣流光）

独立粒子系统，每个粒子沿**螺旋轨迹**从花心飞向花瓣尖，抵达后淡出并循环再生。
手势「张开」的瞬间会触发 `uBurst` 脉冲，整批粒子瞬间加速：

```glsl
float speed = aSpeed * (0.10 + uSpread * 1.45 + uBurst * 2.2);
float twist = (1.0 - life) * 2.4;        // 起点扭转大，终点归零 → 螺旋轨迹
```

### 6. 逸散花粉 / 冲击波光环 / 吹散

- **花粉**：从花朵表面逸散的光点，用 `smoothstep(0.25, 0.75, uSpread)` 做门槛，
  保证**花苞状态完全安静**，不破坏「闭合」的观感
- **光环**：状态突变时从花心扩散一圈光点，带节流
- **吹散**：挥手时沿粒子径向向外推一把，强度衰减后花瓣自己飘回来

## 手势识别是怎么做到的

`js/gestures.js` 从 21 个关键点里提取信号，全部**用手掌尺寸做归一化**，
所以手离镜头远近不会误触发。

| 信号 | 算法 |
|---|---|
| 手指伸展 | 「腕→指根→指尖」夹角，**阈值按指长自适应**（见下） |
| 拇指伸展 | 「拇指尖→食指根 / 掌宽」，实测张开 0.47、握起 0.34 |
| 旋转角 | `atan2(中指根 - 手腕)`，累积后处理 ±π 跳变 |
| 捏合 | 「拇指尖↔食指尖 / 掌宽」，实测张开 0.92、捏合 0.07 |
| 挥手 | 掌心水平速度超过阈值 |
| 远近 | 掌长在画面中的占比 |

> 📌 **两个踩过的坑**
>
> **1. 拇指不能用角度判据。** 它朝侧面张开，「腕→根→尖」夹角不可靠。
> 改用「拇指尖到食指根的距离 / 掌宽」后正常。
>
> **2. 四指不能共用同一个阈值。** 手指越短，握起来时夹角越难变小。
> 实测握拳时各指伸展度：食指 1.45、中指 1.71、无名指 1.95、小指 **2.22**——
> 小指明显偏大。若四指共用 0.55 的阈值，**握拳时小指会被误判为伸出**，
> 导致「握拳」被识别成「伸出一根手指」。
> 现在阈值按指长自适应（短指要求更直），`_test/gestures-test.mjs` 覆盖了这个用例。

## 亮度调参记录

这是本项目最难的调参点，前后走了四次弯路，记录下来避免重复踩坑。

### 关键认识：不能只看「全画面平均亮度」

前两次我用「整幅画面的平均亮度」作为指标，结果一直调不准。
问题在于花朵只占画面一部分，剩下的是背景，
于是「平均亮度 110」里混进了大量背景像素，**指标本身就在骗人**。

改用 `_test/perceptual-brightness.mjs` 分别统计后，真相才出来：

| | 花朵平均亮度 | 覆盖率 | 近黑占比 |
|---|---|---|---|
| 调参前（花苞） | **223 / 255** | 11% | **85.6%** |
| 调参前（绽放） | 171 | 50% | 40% |

**花朵像素本身已经接近纯白（223/255），根本不暗。**
真正的观感问题是：**花朵太小、背景 85% 是纯黑**——
所以它读起来不是「一个明亮的东西」，而是「一个亮的小东西漂在虚空里」。

也就是说，用户说的"太暗"，实际要解决的是**画面占比与背景层次**，不是粒子亮度。
继续加粒子亮度只会过曝。

### 四次弯路

| 阶段 | 结果 | 问题 |
|---|---|---|
| 初版 | 全屏白光 | 颜色值放到 1.4，直接烧白 |
| 过度修正 | 平均亮度 **4/255**、暗部 93% | 压得太狠，看不清 |
| 提亮过头 | 平均 230、过曝 77% | 花瓣细节全丢（边缘清晰度 21 → 2.9） |
| 只看平均亮度 | 平均 110 但观感仍暗 | 指标选错，方向也错 |
| **当前** | 花朵 170~207、覆盖 19~63%、背景 9~21 | ✅ |

### 最终手段

1. **提高画面占比**：粒子数 12000 → 18000，花朵半径 2.35 → 2.72
2. **消灭纯黑背景**：
   - 星尘 900 → 3200 颗，配色从单调灰蓝改为冷蓝/淡紫/粉/金四色
   - 新增**星云层**（全屏柔和色雾，fbm 噪声缓慢流动）
   - 效果：绽放态近黑占比 40.3% → **23.9%**，背景亮度 14.2 → **21.3**
3. **粒子本体与泛光分工**：粒子负责「清晰的花瓣结构」，泛光只负责「光晕」

### 判断泛光是否健康

不能只看亮度，要看**边缘清晰度**（画面梯度）：

- 健康的泛光让清晰度**上升**（19 → 24，加了光晕但保留结构）
- 过强的泛光让它**暴跌**（21 → 2.9，糊成白盘）

用 `_test/base-brightness.mjs` 可以**关掉泛光单独测粒子本体**：
如果本体就已过曝（实测曾达 20%），那再怎么调泛光参数都是白费力气。

### 花心压制要随绽放程度变化

花苞本来就聚成一团，此时压花心等于把整个花苞压暗（实测掉到 6/255）：

```glsl
float stackAmt = max(localSpread, uMorph);
float suppress = mix(1.0, coreMask * coreMask * 0.72 + 0.18, stackAmt);
```

### 当前指标

用 `_test/brightness-check.mjs` 量化：

| 状态 | 花朵平均亮度 | 覆盖率 | 背景亮度 | 近黑占比 |
|---|---|---|---|---|
| 花苞 | 207.3 | 19.1% | 9.2 | 75.0% |
| 半开 | 184.9 | 38.9% | 20.3 | 43.7% |
| 绽放 | 169.6 | 62.5% | 21.3 | 23.9% |

## 核心算法

### 1. tension：手掌张开度 ∈ [0, 1]

单一指标很容易被手的姿态、远近、个体差异干扰，所以**融合三个互补特征**：

设 21 个关键点中，指尖为 `TIPS = [4,8,12,16,20]`、指根为 `MCPS = [1,5,9,13,17]`。

**特征 A — 指尖/指根距离比（权重 0.5，主特征）**

```
d_tip = Σ |wrist → tip_i|
d_mcp = Σ |wrist → mcp_i|
A_raw = d_tip / d_mcp           实测：握拳 ≈ 1.29，完全张开 ≈ 3.45
A     = normalizeRange(A_raw, 1.20, 2.60)
```

**特征 B — 手指伸展度（权重 0.3）**

对每根手指算「腕→指根→指尖」的夹角 θ，伸直时 θ→π，弯曲时 θ 变小；再用该指长度占比 `w_i` 加权，避免短指干扰：

```
B = Σ w_i · normalizeRange(min(θ_i, θ_pip + 0.35), 1.20, 3.00) / Σ w_i
    w_i = |wrist → tip_i| / d_tip
```

**特征 C — 手指伸展的一致性（权重 0.2）**

用「各指尖到掌心距离」的变异系数 `cv = σ/μ` 判断是**整只手**在张开，还是只伸了一两根手指：

```
C = 1 - normalizeRange(cv, 0.10, 0.62)
```

**融合 + S 形拉伸 + 平滑**

```
tension_raw = 0.5·A + 0.3·B + 0.2·C
tension     = smoothstep(0, 1, tension_raw)          // x²(3-2x)
smoothed   += (tension - smoothed) * 0.28            // 抑制抖动
```

> 📌 **为什么归一化区间这么宽？**
> 早期版本把 A 的范围设成 `[1.05, 1.85]`，结果手指**刚松开一点就饱和成 1**，手势退化成开关而非连续渐变（实测 openness 0.15 就已达满绽放）。
> 现在的区间基于实测数据标定，整条 0→1 曲线都能用上：

| 手部张开程度 | tension | spread | 状态 |
|---|---|---|---|
| 0.00（握拳） | 0.07 | 0.00 | 花苞 · 闭合 |
| 0.25 | 0.40 | 0.15 | 初绽 · 微开 |
| 0.50（半开） | 0.87 | 1.00 | — |
| 1.00（全张） | 1.00 | 1.00 | 怒放 · 极盛 |

尺度无关：把手放大 1.6 倍（模拟离镜头更近），tension 变化 < 0.12。

### 2. tension → spread：阈值与平滑过渡

```js
// tension < 0.32 → 0（花苞）；tension > 0.66 → 1（绽放）；中间 smoothstep
t         = clamp01((tension - 0.32) / (0.66 - 0.32))
spread    = t * t * (3 - 2 * t)
```

### 3. 缓动

```js
currentSpread += (targetSpread - currentSpread) * 0.1
```

需求给定的 `0.1` 是 60fps 下的经验值。为了在 30Hz / 120Hz 屏幕上手感一致，代码里做了**帧率归一化**：

```js
const k = 1 - Math.pow(1 - 0.1, dt * 60);
currentSpread += (targetSpread - currentSpread) * k;
```

实测 60Hz 与 30Hz 在同一段真实时间内收敛到同一水平（误差 < 0.01）。

### 4. 花朵几何：极坐标花瓣函数

花瓣轮廓用玫瑰线型函数生成：

```
r(θ) = R · [ base + amp · |cos(p/2 · θ)|^sharp ]      p = 花瓣数
```

- `sharp` 越小花瓣越圆润，越大越尖锐（取 0.75 得到圆花瓣而非星形尖刺）

为了让花瓣有**面**而不是一条线，对每片花瓣建立局部二维坐标 `u ∈ [-1,1]`（宽度）、`v ∈ [0,1]`（长度）：

```
halfWidth(v) = L · 0.26 · sin(π · v^0.72) · (1 - 0.26v)
x = petalLen·v·cos(θ) - halfWidth·u·sin(θ)
z = petalLen·v·sin(θ) + halfWidth·u·cos(θ)
y = 外翻卷曲 + 浅碗形 + 内层抬高
```

> 📌 **两个关键坑（都踩过）**
> 1. `u` 必须**均匀分布**。用 `sqrt(rand())` 会把粒子推到 `|u|≈1` 的边缘，花瓣变成一个**空心的 V 形描边**，中间没有肉。
> 2. 抖动/噪声幅度必须很小。花朵半径仅 ~2.35，抖动超过 ~0.04 就会把花瓣轮廓糊成一团**没有形态的星云**。

### 5. 位置插值在 GPU 完成

每个粒子额外携带一组 `aPosBud`（花苞位置）：

```glsl
vec3 pos = mix(aPosBud, position, localSpread);
```

切换状态时 **CPU 零开销**，1~2 万粒子也只上传少量 uniform。此外还有：

- **逐粒子延迟**：按花瓣角度与层号错开绽放时刻，形成波浪式开合
- **呼吸**、**涡流自转**（幅度克制）、**手指跟随平移**
- 每帧仅更新 `uSpread / uHand / uHandVel / uTime`

### 6. 渲染与光晕

- `AdditiveBlending` + 圆形柔边粒子（`gl_PointCoord` 算径向衰减）
- 片元着色器做「实心核心 + 柔和外晕」两层叠加
- `UnrealBloomPass` 泛光，强度随绽放程度增强

> 📌 **亮度预算是这个项目最难的调参点。**
> 加法混合下 1~2 万个粒子互相叠加，极容易**整体过曝成纯白团**，丢掉全部花瓣细节。当前做法：
> - 几何体里的颜色夹在 `1.0` 以内（早期版本放到 1.4）
> - 片元里 `alpha` 压到 `core*0.42 + halo*0.34`
> - 泛光阈值提到 `0.52`，只让最亮的粒子发光
> - 花心按半径降密，避免三层花瓣在原点堆叠烧成白斑

particles: {

## 稳健性设计

**摄像头权限**——错误按类型给出可操作的提示，并自动兜底：

| 错误 | 提示 |
|---|---|
| `DENIED` | 引导到地址栏权限图标重新授权 |
| `NOT_FOUND` | 未检测到摄像头，建议用自动演示 |
| `IN_USE` | 提示关闭会议软件等占用程序 |
| `INSECURE` | 提示需 `http://localhost` 或 HTTPS |
| `NO_API` | 建议更换现代浏览器 |

权限被拒后 2.2 秒自动切到自动演示，保证用户仍能看到效果。分辨率不被支持时自动降级重试。

### 性能自适应

按帧率**分级**调整，而且**支持恢复**：

| | 阈值 | 动作 |
|---|---|---|
| 降级 | 低于 26 FPS 持续 3 秒 | 逐级降：粒子 ×0.78/0.62/0.48，泛光 ×0.75/0.55/0.35 |
| 恢复 | 高于 52 FPS 持续足够久 | 逐级升回去 |

> 📌 **降级不关泛光，只按比例缩放。**
> 早期版本在降级时直接 `setBloomEnabled(false)`，泛光一关画面立刻变平，
> 用户反馈「画质有点低」——根因就在这里。
>
> 📌 **降级重建几何体时，必须同步重建形态数据。**
> 早期版本只换了 geometry，导致 `shapeData` 仍是旧粒子数的数组，
> 而 `setShape` 里有一句长度校验会 `return false`，
> 于是**降级之后所有形态切换都静默失败**（按钮点了没反应）。
> 现在 `setShape` 遇到长度不匹配会打 `console.error` 而不是静默失败。

用 `?nodegrade=1` 可以完全关闭性能自适应（始终满配），排查画质问题时很有用。

**移动端**——自动降低粒子数、粒子尺寸与泛光强度，限制 DPR。

**其他**——标签页隐藏时暂停推理省电；`dt` 夹紧防止切回时画面跳变；全流程无外部依赖即可离线运行。

### 遇到问题时

在浏览器按 F12 打开控制台，输入：

```js
__bloomStatus()
```

会打印识别链路的关键状态（模型来源、是否就绪、是否检测到手、send 失败次数等），
便于判断是「模型没加载」「引擎没初始化」还是「确实没检测到手」。

常见情况：

| 现象 | 原因 | 处理 |
|---|---|---|
| 状态一直停在「正在初始化识别引擎…」 | 正在下载 18MB 模型 | 等待；或确认 `vendor/mediapipe/` 完整 |
| 提示 `No subgraph` / `'Not ' should be 'TFL3'` | 模型文件被截断 | 核对 `hand_landmark_full.tflite` 是否为 5,478,688 字节 |
| 摄像头灯亮但花朵不动 | 手不在画面内 / 光线太暗 | 让整只手进入画面，正对光源 |
| 「识别就绪」但 `hasHand: false` | 正常，还没看到手 | 把手放到镜头前 |
